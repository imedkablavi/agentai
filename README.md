# AgentAI

AgentAI is a local-first TypeScript assistant/CLI with Arabic, Turkish, and English intent handling. The current architecture treats model/intent confidence as **interpretation metadata only**: confidence never grants permission to execute an impactful operation.

> Security boundary: AgentAI is designed for user-authorized operations on the local machine and the explicitly selected workspace. It is not a sandbox for untrusted code or untrusted skills.

## What changed in the security architecture

The execution path is now centralized:

```text
user input
   ↓
intent / skill routing        confidence = interpretation only
   ↓
ExecutionCommand
   ↓
ExecutionPolicy              action + target + platform + scope policy
   ├─ deny
   ├─ allow read/non-impacting action
   └─ preview → command-bound approval → execute
                                      ↓
                              redacted AuditTrail
```

Key properties:

- Central action allowlist: a skill cannot introduce arbitrary shell actions simply by returning a low-risk command.
- Exact application allowlist for built-in application actions.
- Workspace path boundary based on normalized relative paths and symlink checks.
- Protected paths include VCS/dependency/build directories and common credential/key files.
- Impactful actions use a preview and an approval bound to the exact pending command for five minutes.
- Approval phrases must be exact. `yes and shutdown` is not treated as approval.
- A new unrelated input cancels stale pending approval rather than reusing it.
- Scheduled execution cannot satisfy an interactive approval requirement, so approval-gated commands are not auto-run by the scheduler.
- Subprocesses use fixed executables plus argument arrays rather than shell-interpolated command strings.
- Developer patch application uses an atomic write, private backup, post-write validation, and rollback on validation failure.
- Audit events are structured and redacted before persistence.
- Runtime state is stored outside the repository by default.

See [SECURITY.md](SECURITY.md) and [docs/THREAT_MODEL.md](docs/THREAT_MODEL.md) for boundaries and assumptions.

## Install and run

Requirements:

- Node.js 18 or newer
- npm
- Platform tools required by the specific feature you use (for example Git for Git-aware developer output)

Development checkout:

```bash
npm ci
npm run check
npm run build
npm start
```

To make the local checkout available as an `agentai` command:

```bash
npm run build
npm link
agentai
```

The package exposes:

- CLI: `agentai` → `dist/main.js`
- Library entry: `dist/AIAssistant.js`
- Type declarations generated by TypeScript

The repository does **not** claim that this package is published to npm unless a release explicitly says so.

## CLI privacy controls

Useful local commands:

```text
memory
memory retention <days>
memory clear
memory clear --confirm
memory clear short
memory clear short --confirm
audit
audit clear
audit clear --confirm
tasks
tasks clear
tasks clear --confirm
```

Deletion commands use a two-step CLI flow. `memory clear` shows what will be deleted; the `--confirm` form performs the deletion.

## Runtime data and retention

By default AgentAI stores private runtime state under:

```text
~/.agentai/
├── audit/audit.jsonl
├── memory/
└── scheduler/tasks.json
```

Override the base directory with:

```bash
AGENTAI_DATA_DIR=/private/path agentai
```

Privacy defaults:

- Short-term conversation memory is in-process only and is **not persisted** by default.
- Long-term pattern inference from repetition is **off** by default.
- Explicit persistent memory requests require approval.
- Long-term retention defaults to 30 days and is configurable from 1 to 3650 days.
- Short-term and long-term memory can be deleted independently or together.
- Preferences are separate from remembered content; `memory clear --confirm` keeps preferences.
- Scheduler snapshots exclude conversation history and active-topic context.
- Audit files are redacted before write and rotated with a bounded local size.

POSIX file/directory modes are set to private values where supported. Windows/non-POSIX filesystems do not provide identical chmod semantics, so OS account/file ACL configuration remains part of the host security boundary.

## Built-in skills

- Application open/close for a fixed list of known application identifiers
- Web and YouTube search
- System session/power actions on Windows, always approval-gated
- File read/inspect within the workspace
- Developer test and validated patch-preview workflow
- Explicit memory storage
- Selection from prior search results
- Scheduling of supported intents

A skill is not a security authority. Its `ExecutionCommand` is evaluated by `ExecutionPolicy` before execution.

## Approval model

Examples of operations requiring approval include:

- Windows shutdown/restart/lock/sleep
- Closing an application
- Running project tests
- Persisting a memory
- Applying a staged developer patch

A preview produces a command-bound pending record with an expiry. The exact approval token (`Yes`, `Evet`, or `نعم`, plus documented exact aliases) can approve that record. Compound text is not accepted as an approval token.

A developer fix has two phases:

1. Generate a proposed replacement and validate it using a temporary workspace-scoped preview file. The target file is not modified.
2. After explicit approval, atomically write the staged content, run project validation, and roll back if validation fails.

## Scheduler behavior

New scheduled tasks are created disabled and require explicit enable approval. Scheduler state is private local data, not repository content.

When a task becomes due, its resulting `ExecutionCommand` is evaluated in `scheduled` mode. Any command that requires interactive approval is denied for that scheduled run rather than silently approved.

## Security tests

The security-oriented test suite covers, among other cases:

- destructive commands do not execute because confidence is high
- exact command-bound approval and cancellation
- compound approval text rejection
- action/application allowlists
- path traversal and sibling-prefix escapes
- protected path rejection
- scheduled approval bypass prevention
- secret redaction before audit persistence
- short-term memory non-persistence by default
- memory retention and deletion
- scheduler snapshot minimization
- atomic patch rollback after failed semantic validation
- ambiguous/compound intents

## Non-goals and remaining host boundaries

AgentAI does not claim to:

- sandbox malicious local Node.js modules or third-party skills
- provide OS-level privilege separation
- securely erase data from SSD/filesystem snapshots/backups
- guarantee network search-provider availability
- prove that generated code is correct merely because syntax/tests pass
- provide universal application/process discovery across Linux desktop environments
- provide Linux power/session control in the current policy

Do not run AgentAI with elevated/admin privileges unless a specific, understood host-level reason requires it.
